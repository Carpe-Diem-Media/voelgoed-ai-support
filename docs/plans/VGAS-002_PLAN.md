# VGAS-002 implementation plan

**Goal.** Prove that one eligible signed Chatwoot message can produce one durable fixed reply or a handoff to staff, including recovery when a worker restarts or a POST has an uncertain outcome.

**Architecture.** Phoenix verifies the original request bytes. Ash actions record receipt, admission, ownership and delivery decisions on the shared PostgreSQL Repo. Oban runs bounded processing and recovery jobs. The Chatwoot boundary uses a deterministic fake for local and CI acceptance.

**Base.** Plane VGAS-13, Backlog when read for this plan. Plane lists VGAS-12 (VGAS-001) as its blocker and VGAS-14 (VGAS-003) as downstream. The planning base is PR #7, `origin/feat/vgas-001-staff-authz` at `cf70bd58c56c76fcb5277efbf1bf7f5cbd0b3eeb`, verified after `git fetch origin`. Read the exact commit for predecessor code. Start implementation on a branch from updated `origin/main` after VGAS-001 merges and the ticket becomes eligible. Recheck the interfaces below against the merged changes. The planning worktree stays on its original branch. This document is the only deliverable from the planning turn.

Closure keeps automation inhibited and never acts as a return or resend. Hold live staff commands behind the VGAS-001 staff-use gate. ## 3. Resource design

Every business record has a native UUIDv7 PK and immutable UTC creation time. Mutable records have UTC update time. Use bounded strings, closed typed enums and typed projections for embedded data. Apply NOT NULL, enum and nonnegative checks where relevant. Qualify external IDs by the trusted installation and account, then require inbox and conversation consistency. Use lossless positive signed-64-bit Chatwoot IDs in candidate fixtures. Verify the deployed representation in F07. Do not derive ordering from UUIDs. Restrict deletion on historical references. The slice has no paid calls or money fields. Future cost accounting uses integer nano-USD.

Use separate action/target-scoped actor structs for ingress, support processing, delivery and reconciliation. Derive scope from trusted config and loaded qualified records, then compare it to the action and actual row. Deny anonymous calls, incompatible actor/action pairs and scope drift even on direct invocation. Do not accept actor, credential ref, state, epoch, deadline, arbitrary JSON or target selection from webhook or staff request data. Staff actions require the current admin or support-operator role as listed below, with no implied admin inheritance of support-operator authority. Expose narrow projections for reads, and leave all unlisted actions unavailable.

- **Intelligence.Assistant.** Slug (unique), name, customer-support kind, public/internal audience ceiling, status, active revision FK belonging to the assistant, security epoch, disabled time. Admin `create` initializes DISABLED. `activate` requires a published current config and verified test permissions. `disable` and restrictive config changes bump security epoch and fence queued/unsent work. `retire` requires disabled, inhibited/drained work and is terminal. Admin and scoped support `read_configuration` see safe fields only. Audit configuration changes. An active row requires an active revision pointer.
- **Intelligence.AssistantRevision.** Assistant FK, revision number, state, fixed workflow/template version, approved test locale/response policy and hash, creator/publisher staff FKs and publication time. Delay provider/model, knowledge grants, pricing and inference options until used. Unique assistant/revision number, supporting composite key for the active pointer, partial unique published row per assistant. Admin `create_draft` assigns next revision under assistant lock, `edit_draft` and `discard` only in DRAFT. `publish` compares expected current pointer and validates fixture policy, supersedes the old revision and switches pointer atomically. Reject stale publication. SUPERSEDED and DISCARDED are terminal. Rollback config through a new reviewed revision. Expose only scoped revision projections to workers. Pin revision in each run and check current restrictions independently.
- **Support.InboxBinding.** Installation ref, account/inbox IDs, assistant FK, status, mode, server credential ref, bounded handoff settings and security epoch. Unique qualified inbox, immutable external key, supporting composite key for session FK. Admin `create_draft`, `enable` with verified association/routing/current assistant, `disable`, `rebind` while disabled with fresh evidence and generation, `change_mode` with authorization and new security epoch, `retire` after inhibition from DISABLED. DRAFT/DISABLED can enable after verification. ENABLED can disable. RETIRED is terminal. Rebinding changes the assistant/config for the same qualified inbox. A different inbox requires its own verified identity and is out of this slice. Read safe config by scoped ingress/support/delivery/reconciliation actors. Default disabled. Only deterministic test config can exercise a public-write path here.
- **Support.SupportSession.** Binding FK with qualification, installation/account/inbox/conversation, verified contact reference if needed for quotas, generation, state, ownership epoch, durable human inhibit/history, observed status, assignee type/ID and reply capability, observation time, close time/reason, correlation ID. Unique qualified conversation/generation and partial unique qualified conversation where state is nonterminal. Lock authority rows before allocating a generation even when the prior generation is closed. Scoped ingress/support `register` creates UNVERIFIED. Support `activate_bot` requires fresh verified bot assignment and current permissions. `observe_human_takeover` from UNVERIFIED/BOT_ACTIVE makes HUMAN_ACTIVE and fences work. A qualified human observation in HANDOFF_PENDING can confirm the handoff, subject to delivery evidence rules. Support/operator `request_handoff` changes BOT_ACTIVE to HANDOFF_PENDING and atomically inhibits, bumps epoch, cancels provably unsent work and stages a status intent. Support/reconciliation `confirm_handoff` moves to HUMAN_ACTIVE on verified goal. Failure leaves HANDOFF_PENDING and visible to staff. Operator `return_to_bot` requires HUMAN_ACTIVE, explicit authority, fresh external eligibility, no unresolved public intent and a fresh epoch. It uses only new work. Support/reconciliation/operator `close` requires verified resolution or authorized termination. CLOSED is terminal. Reopening uses a new generation and inherits outstanding human restrictions and UNKNOWN hold across generations.
- **Support.InboundEvent.** Trusted installation/account/inbox/conversation, event type, optional external message ID or documented stable event ID, optional matched session FK, receipt time, optional untrusted occurred time, decision/processing disposition and timestamps, ingress state/reason and correlation ID. Use separate partial unique indexes for qualified message key and verified non-message stable key. No universal payload-hash or timestamp identity. Ingress `register` sets ACCEPTED, `dispatch` makes DISPATCHED with the job, `ignore` and `quarantine` record terminal IGNORED/QUARANTINED. ACCEPTED is internal to T01 and never visible after commit. Keep processing disposition separate from terminal receipt state. Scoped workers record coverage, expiry or qualification outcome once, and may reclaim only unfinished processing under a higher read generation. Store minimal durable refs and retain the dedupe key even after content would be eligible for purge.
- **Support.SupportRun.** Session and pinned revision FKs, parent link and turn UUIDv7, ownership and policy epoch snapshot, claim generation, lease, deadline, batch cutoff, ordered input coverage and watermark, attempts, retry eligibility time, decision/reason and correlation, start/finish times. Use a relational coverage mapping keyed by qualified inbound message and run, with one current coverage owner per eligible message and historical links preserved. A partial unique index on session for QUEUED/RUNNING/RETRY_WAIT enforces a single active run, with the locked session check also covering pending/claimed/unknown delivery and earlier generations. Support `queue`, `claim`, `complete`, `schedule_retry`, `requeue`, `supersede`, `cancel`, `fail`; reconciliation `recover_expired_claim`. QUEUED → RUNNING only on admission and current token. RUNNING → COMPLETED commits the validated decision and outbox or the explicit no-send result. RUNNING → RETRY_WAIT → QUEUED only for safe bounded work. Active → SUPERSEDED transfers outstanding coverage transactionally to a successor, active → CANCELLED on revoked eligibility, active → FAILED on exhaustion or permanent error with a triage outcome or permitted handoff. All four target states are terminal. COMPLETED records the decision. Delivery has its own lifecycle.
- **Support.OutboundDelivery.** Session FK and nullable same-session run FK, purpose, kind, visibility, qualified destination, immutable template reference/hash or minimal fixed payload, stable operation correlation token, epoch snapshot, state, attempt count, lease and claim generation, dispatch authorization marker, read reservation sequence/budget, deadline, external message ID, reconciliation fact/reason, timestamps. Unique reply per run, unique operational handoff by session/epoch/purpose, correlation token unique. CHECK allowed payload/visibility per purpose, qualified acceptance ID for SENT public message, and lease/claim invariants. In scope are public_reply and handoff_status. Optional handoff_notice is skipped under G012. Support `prepare` creates PENDING only in T04/T05. Delivery actor `claim`, `authorize_dispatch`, `confirm_sent`, `mark_unknown`, `cancel`, `fail` and carefully guarded `safe_retry` operate on exact state/generation. Reconciliation actor can recover, read back and settle UNKNOWN with applicable evidence. Current scoped operator `abandon` closes UNKNOWN with an audit and human inhibit. See §5 for the precise transitions.
- **Supporting persistence.** Governance owns a singleton global control row, always seeded disabled, with mode/epoch and the runtime emergency inhibit. Admin `disable_automation` immediately fences old permission. `enable_automation` requires explicit authorization and fresh checks, with fake mode the only enabled test path. An affected binding's operational circuit opens on definitive auth/config failure or when the bounded transient policy trips, denies writes, and permits a single bounded read probe after cooldown. A successful probe can close the circuit without changing admin enablement. The live trip threshold is an owner setting. Rate windows have unique scope/type/window start, checked nonnegative counts and bounded expiry. Use verified scope and internal idempotent event/turn keys. Keep an atomic operational audit and read projection for failed handoff, missed deadlines and UNKNOWN. Store no raw input text or attachments, and use code-owned fixed output references. G029 purge/hold and replay policy remain release prerequisites when content or real customer metadata is introduced. Retain unresolved refs and dedupe tombstones. Do not make deleted content, expired metadata or restore grant permission to resend.

## 4. Ingress, admission and durable batches

1. Match the one server-configured installation before reading bytes. Allow only POST and JSON. Bound declared and actual body, total read time and per-read timeout. Consume chunks before parsers, at most 64 KiB for the candidate. Require one canonical timestamp and one signature header. F06 implements HMAC-SHA256 over literal `timestamp <> "." <> bytes`, hexadecimal `sha256=` digest and inclusive ±300 seconds for CE v4.18.0 candidate `9f920b549c14491a4e587687a3eed5d21c6ccc7d`. Authenticate before JSON decode. Decode with Jason 1.4.5 `objects: :ordered_objects` and reject duplicate members in validated objects before converting them to maps. The default map decoder loses duplicates. Reject malformed or conflicting identity fields. See `deps/jason/lib/{jason,decoder,ordered_object}.ex` and the [candidate Chatwoot signing source](https://github.com/chatwoot/chatwoot/blob/9f920b549c14491a4e587687a3eed5d21c6ccc7d/lib/webhooks/trigger.rb#L37-L56). Return generic 401/400/413/415 as applicable. Mismatched authenticated scope returns generic 403 under the F06 candidate with no work. Persist only bounded safe outcomes for supported ignored/quarantined events. Prevent body, secret and payload leakage in errors, telemetry and logs.
2. In T01, resolve and lock the exact local binding and look up the stable receipt by qualified key. Under the single-binding slice, that lock serializes duplicate registration. The unique index is the final boundary. If a constraint race nevertheless aborts the transaction, read the committed winner in a new authorized transaction and acknowledge only a matching durable terminal receipt. Insert the named event action and `Oban.insert` of the worker's job in one `Repo.transact` on the same Repo. Put only internal UUIDs in job args. A signed, qualified public human outbound event with verified sender shape may inhibit at receipt time on the same transaction, including the first human observation. If sender proof is insufficient, deny the reply pending qualified reconciliation. Commit before 204. Return generic HTTP 500 on a rolled back receipt/enqueue/inhibit. The [candidate webhook sender](https://github.com/chatwoot/chatwoot/blob/9f920b549c14491a4e587687a3eed5d21c6ccc7d/lib/webhooks/trigger.rb#L116-L124) explicitly classifies 429 and 500 as retryable for the agent bot. Verify deployed retry and fallback behavior in F07. Duplicate 204 preserves original receipt time and cannot recreate a job or consume another count.
3. A public customer text event requires fresh qualified conversation/contact/ownership evidence and may join a batch. Human outbound and supported status/assignment observations update ownership or reconcile. Bot outbound may supply positive qualified delivery evidence. Private notes and system messages never enter a batch or trigger inference, and unsupported attachments are not fetched. Edits/deletes with verified identity invalidate affected coverage where the candidate supports them. Unkeyed state observations drive bounded verification of current state and do not become new turns. Include a bounded qualified read for a missed event or changed input before dispatch.
4. Use one lock order for mutation paths, staff row when needed, global control, assistant, binding, qualified session, target rows in deterministic order, then ordered counter windows. With the single binding, its lock also serializes first session allocation. No locks span HTTP or task waits. Recheck UTC time after contended locks. Establish the parent deadline from the original eligible receipt plus 45 seconds, including queue and debounce. Once overdue, record disposition for operator triage without a new automatic handoff. The verified history orders messages. Never use arrival time, event time or UUID as external message order.
5. T02 checks distinct eligible messages before batching. Use fixed UTC windows and candidate defaults of 10/min and 60/hour per qualified contact, 40 admitted response turns/day per contact and conversation, 3,000 characters per input, one active run per conversation, five globally running support runs and 100 pending candidate turns. Reserve applicable inbox/global, queue and worker limits under the same transaction as admission, without partial charges on denial. Full queues must also bound pre-admission receipt work so it cannot bypass the pending-run ceiling. Keep message and turn accounting separate and idempotent. A retry or batch successor cannot reset its counters or deadline. Distinct authorized human handoff and manually routed triage do not consume reply allowance. A capped receipt has a durable reason and visible human path. No automatic limit notices in this slice. Synthetic thresholds can exercise unspecified caps until operational settings are approved.
6. Use a test-configured 1–2s debounce, capped at five seconds from first eligible receipt. Bound batch size and the message/ref projection. At cutoff, claim one ready run under its session lock and allocate a generation and lease. If a new eligible message makes an unsent result incomplete, suppress that result. Preserve uncovered messages durably. Allow one bounded regrouping on the same parent deadline; otherwise route to staff through approved handoff or recorded triage. A completed run with a PENDING intent stays immutable, so cancel its unsent intent and link a successor. If SENDING/UNKNOWN already exists, hold new public work and retain the new message for staff/reconciliation handling. No public replay on resolution, reopening or explicit return.

## 5. Claim, outbox and recovery

- **T04, complete a run.** In a short transaction recheck the session, current ownership/config generations, claim, lease, deadline and coverage watermark. Write the decision and unique delivery intent. Insert the delivery and deadline jobs before commit. A stale or failed transaction leaves no sendable intent. The fixed response is a code-owned synthetic template. Record an explicit no-send outcome in SHADOW/ASSISTED. No external calls in the transaction.
- **T05, request handoff.** Lock the session and affected work. Commit HANDOFF_PENDING, a new ownership epoch, cancellation of pending reply intents, the unique status intent and recovery jobs together. A sending reply with possible POST remains uncertain. A confirmed human takeover needs no status write. A preflight which shows the conversation already human-owned satisfies an existing handoff goal without overwriting the human assignment. Apply the named claim and confirm transitions in one transaction with zero dispatch attempts and record that the goal was already met. The candidate handoff uses explicit `open` only from freshly confirmed pending/configured-bot status and verified routing. A closed reply window does not itself prevent that status handoff. Qualified resolution closes the local session and suppresses the status write. No auto-resolve, toggle-by-omission or reopening. Use the single verified staffed queue in fixtures. Separate team mutation, if needed in staging, requires F07 evidence and a separate guarded intent for each side effect.
- **T06, claim and dispatch.** Reserve the applicable bounded preflight read under lock with a monotonically increasing read sequence. Call the adapter outside the transaction, then use the result only if its reservation, qualifier tuple, ownership and deadline still match after reacquiring locks. PENDING → SENDING acquires an exclusive generation and lease and schedules lease recovery in the same transaction. Immediately before calling the adapter, verify committed state, current global/binding/assistant epochs and mode, scope, session epoch, applicable remote eligibility observation, freshness, deadline, read sequence and remaining lease for the entire request plus margin. Mark dispatch authorized for that generation in a short guarded transaction. Once that marker can commit, a crash is treated as possible dispatch even if the process actually died just before POST. A stalled pre-marker worker cannot enter the adapter after recovery invalidates its claim. Exiting with a proof that dispatch was denied and no request entered the adapter becomes CANCELLED and releases the slot. A definitive pre-send failure becomes FAILED where appropriate. Invalidation never labels a possibly sent intent CANCELLED.
- **Settle.** Only the current live claim can settle its own result. SENDING → SENT on verified, same-destination acceptance with a message ID, or qualified confirming read for an achieved handoff goal. SENT records Chatwoot acceptance/goal confirmation. SENDING → UNKNOWN on timeout, reset, uncertain response, lost worker after dispatch authorization, stale settlement or uncertain handoff read-back. Record the initial reason, minimum required refs, and enqueue read-only reconciliation. A late result cannot overwrite recovery, reopen a read budget or authorize dispatch. SENDING → PENDING is restricted to positive no-effect proof within policy, such as a fenced expired claim with no dispatch authorization. No automatic second POST in the local slice. Set the write worker's `max_attempts: 1`. Assign preflight scheduling, lease expiry and bounded reconciliation to separate jobs. Keep attempt budgets on the domain record so Oban rescue and replacement jobs cannot reset them. Treat a 403 after POST as uncertain without F07 proof. If no-effect failure is definitive, use FAILED. SENT/FAILED/CANCELLED/ABANDONED are terminal.
- **Recover.** On expiry, recover safe local work under a higher generation. Never return an authorized or potentially active external request to PENDING. Classify it UNKNOWN and retain the block even if a request task still lives. The fake caller is synchronous, bounded and owned by the worker. Test a still-running blocked adapter, late result and duplicate job independently of Oban rescue. Recovery may observe but must not launch concurrent writes. Separate preflight/confirmation/reconciliation reservations fence old responses after a later read, deadline or operator disposition. Cap safe reads at three within the applicable budget. Use bounded backoff of 1s/3s where applicable and honor Retry-After only inside the deadline. Handoff preflight, immediate confirmation and automatic read-back share three reads and a provisional five-minute intent deadline. Unknown public-reply verification is read-only, with a separate recovery deadline and a three-read ceiling. Use the provisional five-minute G013 recovery window in fixtures, measured from the first committed UNKNOWN disposition. Replacement jobs cannot extend the deadline. Use individual deadline/lease jobs plus a bounded Oban Cron sweep for discarded/lost jobs and stranded receipts. Sweep old work in stable order without resetting any deadline. No custom scheduler. Pending handoff failure remains inhibited and visible. Exhausted reconciliation records a durable recovery failure while the outcome stays UNKNOWN.
- **Reconcile and close.** A reply matches only reliable round-tripped operation correlation plus verified installation/account/inbox/conversation, sender bot, correct visibility/kind and a qualified external message ID. Matching text, missing record or exhausted pagination is insufficient. UNKNOWN → SENT on positive evidence. UNKNOWN → FAILED requires definitive no effect and abandonment. UNKNOWN → ABANDONED requires a current authorized operator, explicit disposition and typed reason, qualified evidence reference or acknowledgement of uncertainty, and immutable audit in the same transaction. A resolved read after a handoff POST closes the session and leaves the write UNKNOWN. It cannot prove the open handoff goal. Store verified handoff goal separately from attribution of which remote actor changed state. Hold new public turns across session generations until the uncertainty is resolved or responsibility has transferred to staff, with no implicit renewed permission in either case. A separate, explicitly reviewed future delivery is out of VGAS-002. Any new bot turn after manual abandonment requires an explicit return and fresh eligibility.
- **Residual race.** Remote ownership, status or routing can change after our last qualified read or local dispatch check. Locking the local row or killing the local worker cannot recall a request already in transit. The adapter must never send a status mutation after observing resolution.
