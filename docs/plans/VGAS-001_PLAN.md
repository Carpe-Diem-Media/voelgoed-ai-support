# VGAS-001 implementation plan

Plane VGAS-12 · Establish a reproducible application and staff authorization boundary

**Goal.** Make the existing Phoenix app reproducible and prove that each staff member gets only their current local permissions after Entra sign-in.

**Architecture.** Use one Phoenix app and one AshPostgres Repo. Accounts owns staff identity, lifecycle and session validation. Governance owns the two-table slice's append-only audit history. Use the native AshAuthentication OIDC flow with the F08 checks at its application boundary.

**Base and scope.** Plan against `origin/main` at `2f7b59265fac73e483e8b1c49934de9a998814f8`. F01 and F08 are the local reference evidence. The F06 Chatwoot spike in PR #5 is independent. This slice covers source, local bootstrap, CI and staff authorization. Chatwoot, editorial UI, AI, live staff access and deployment are outside delivery scope. Use the repository's implementation workflow and track the steps below in order. [F06 PR](https://github.com/Carpe-Diem-Media/voelgoed-ai-support/pull/5)

## 2. Build Accounts and Governance

- [ ] Create `lib/voelgoed_ai/accounts.ex`, `lib/voelgoed_ai/accounts/staff_user.ex`, `lib/voelgoed_ai/accounts/staff_access.ex`, `lib/voelgoed_ai/accounts/staff_lifecycle.ex`, `lib/voelgoed_ai/governance.ex` and `lib/voelgoed_ai/governance/audit_event.ex`. Register both domains in `config/config.exs`. Use Ash policies and domain `authorize :always`. Use fixed typed roles `ADMIN`, `KNOWLEDGE_EDITOR`, `KNOWLEDGE_REVIEWER` and `SUPPORT_OPERATOR`. Roles are additive. ADMIN grants staff management only within this slice and never implies an editorial or support role.
- [ ] Define `StaffUser` on `staff_users`. Use native UUIDv7, exact bounded issuer and subject, a separately validated tenant claim, optional bounded email/display name fields, fixed roles, status, nonnegative bigint `session_generation`, and UTC microsecond timestamps for creation, update, last login, disable and retirement. Leave optional profile fields unset unless a supported use requires them. Use Ash identity `[:identity_issuer, :identity_subject]` backed by a unique index with case-sensitive equality. Keep identity immutable, including after retirement.
- [ ] Expose only named Ash actions through Accounts. Use typed internal actor contexts scoped to verified callback lookup, current-session lookup, one authorized transition, bootstrap provisioning or one audit append. Set these in trusted application code. Policy checks match the actor to its action and target, and deny ordinary sessions calling internal actions. Use a private Ash-authentication context **and** the trusted callback actor on the sign-in read. Do not use `authorize?: false` or an authentication-wide bypass. Treat these checks as boundaries for application callers and HTTP input. Arbitrary code execution inside the BEAM is outside their trust model.
- [ ] Implement the following lifecycle. Any failed guard, conflicting write or audit error aborts the action without issuing a session. Return bounded typed errors internally and generic failures over HTTP.

  - `provision`. A current ACTIVE admin or the controlled bootstrap command creates an INVITED row with explicitly supplied local roles. Require separately verified allowlist evidence binding the configured tenant and exact issuer/subject for this app registration. A duplicate or retired identity conflicts without changing the existing row. Append `provisioned` audit.
  - `sign_in_with_entra` and `authenticate`. Only a verified callback can find the invited or active candidate. Lock it and recheck identity and status. INVITED becomes ACTIVE and records `activated`. ACTIVE stays ACTIVE and records `signed_in`. Update last-login time and issue the local session after commit. An empty role set confers no privileged access.
  - `set_roles`. A current ACTIVE admin changes an INVITED or ACTIVE target's canonical role set. Audit before/after and increment generation on a real change, including revocation or subsequent restoration. An unchanged set produces no mutation or audit. Reject unknown roles and unrelated fields.
  - `disable`. A current ACTIVE admin moves INVITED or ACTIVE to DISABLED, records the UTC disable time, increments generation and audits. Subsequent login and privileged use fail. A duplicate disable changes nothing.
  - `reactivate`. A current ACTIVE admin explicitly moves DISABLED to ACTIVE after verifying the same allowlisted identity, current tenant/registration and intended local roles. Increment generation, clear the current disable marker, and audit the approved reprovision. Require fresh OIDC sign-in for a session. Preserve prior disable evidence in audit.
  - `retire`. A current ACTIVE admin moves DISABLED to RETIRED after revocation is in effect. Set the retirement time, increment generation and audit. RETIRED is terminal and keeps its unique identity and history. Reject all further lifecycle mutations and logins.
  - `read_staff` and `read_self`. Restrict the former to a current ACTIVE admin and the latter to the current authenticated staff member's own limited projection. Field policies and return projections keep private identity and session fields out of response data. Provide internal point reads with scoped actors and no generic list or write interface.

- [ ] Use `Repo.transact/2` with Ash point reads locked via `Ash.Query.lock(:for_update)`. For admin mutations lock the acting and target rows in sorted UUID order, one lock if they are the same row. Recheck expiry, status, generation and explicit admin role under the lock. Provisioning locks the admin and lets the unique index resolve concurrent insertion. Callback exchange finishes before the transaction. Inside it, re-read the candidate under lock, apply the action and append audit in the same transaction. Return `{:error, reason}` to roll back both writes. A callback that commits just before disable may deliver a cookie that is already stale. Each subsequent privileged call must reject it. [PostgreSQL 18 row locking](https://www.postgresql.org/docs/18/explicit-locking.html)
- [ ] Define `AuditEvent` on `audit_events`. Store UUIDv7, typed actor kind and internal actor reference, action, target kind and internal target reference, reason code, correlation UUID, UTC occurrence and insertion timestamps, and typed before/after metadata limited to status, local roles and generation. Require a staff target FK and a staff actor FK when the actor is a staff member. Use a fixed operator reference for bootstrap. Keep pseudonymous internal references access-controlled. Allow only an action/target-scoped internal append and a restricted staff-security read for a current ADMIN. No application update/delete action or cascading delete. Record rejected requests through bounded redacted incident telemetry with a reason code and correlation only. Never pass provider payloads, credentials, raw identity claims or inspection of dependency errors into audit or logs. Document G029's provisional retention and obtain approval before any production purge policy.
- [ ] Generate `priv/repo/migrations/<timestamp>_add_staff_authorization.exs` and commit the two table snapshots under `priv/resource_snapshots/repo/`. Keep the existing foundation migration and extension snapshot intact. Review native UUID defaults, non-null and status/role/generation checks, disable/retirement timestamp constraints, unique identity and restrictive audit FKs. The pinned AshPostgres Repo chooses PostgreSQL's built-in `uuidv7()` for minimum PostgreSQL 18, and Ash provides `uuid_v7_primary_key/1`. Use the actual generated SQL and test it against real PostgreSQL. Keep pgvector installation in the provisioning layer. The existing migration installs Ash functions. [AshPostgres 2.15.2 release notes](https://ash-postgres.hexdocs.pm/changelog.html), [PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html)

## 3. Promote F08 into the Phoenix routes

- [ ] Add `lib/voelgoed_ai_web/staff_auth_controller.ex` and `staff_session.ex` alongside it. - [ ] Keep registration and external identity records disabled and use state, S256 PKCE and a session nonce. Use `openid` with a confidential Web app and `client_secret_post` as the proposed registration mode. Assent 0.3.2 implements that method on its OIDC and OAuth2 paths. F08 used `none`. A deterministic confidential-client test must assert what the adapter sends before claiming local parity, and VGAS-9 must verify it live. [Microsoft authorization code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- [ ] Before following discovery on either leg, require exact metadata issuer equality and validate the three required endpoint URLs and advertised client-auth methods. Extend the F08 HTTPS checks with an allowlist of expected Microsoft hosts and endpoint paths for the selected cloud and tenant metadata. Allow the Microsoft-published shared signing-key path as appropriate. Match the outbound method and URL before sending credentials, and reject redirects or unexpected calls. Use bounded HTTP timeouts, response byte and key-count caps, and no automatic exchange retries. Choose caps with fixture tests and verify compatibility in VGAS-9. Keep the transport substitution test-only. [OIDC Discovery §4.3](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation), [Microsoft OIDC metadata](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)
- [ ] Port `EntraSubject` and `EntraOIDCResponse` validations. Bound compact tokens to 32 KiB and text to 4 KiB as in F08. Require a compact RS256 ID token with `kid`, typed claims and supported headers. Validate a nonempty key set with unique bounded key IDs and RSA modulus of 2048–4096 bits, exponent 65537 and public material only. Reject malformed responses before library processing. Preserve Assent's signature, issuer, audience, expiry and nonce checks. Use the claims of that same verified token to compare the exact issuer, pairwise subject and separate `tid`. Preserve the 1–255 ASCII subject bytes without trimming or case folding. Validate integer time claims and current expiry and not-before. Compare the signed subject and tenant with Assent's returned identity before lookup. The pinned `deps/assent/lib/assent/strategies/oidc.ex` drops protocol claims from the returned map. If claim extraction rereads the token, do so only after successful verification on the trusted callback path and test consistent parsing. Never match or grant roles by email, UPN, `oid`, groups or token roles. [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation), [Microsoft ID token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference)
- [ ] Renew an encrypted and authenticated, Secure, HttpOnly, SameSite=Lax session after commit. Store only staff UUID, generation and bounded expiry, initially the F08 10-minute local candidate, with a trusted registration binding or cookie-key rotation on registration change. Keep tokens and role claims out of the cookie. Each protected action reloads the current staff record and checks expiry, generation, state and the exact role. Clear the browser cookie on sign-out or failed callback. Use a generic failure, no-store responses and log filtering that covers callback params, transport errors and SQL bindings. Keep `/health` outside staff auth.
- [ ] Keep the original F08 suite as a reference. Use deterministic HTTP fixtures under `test/support/` through the real app router. Leave the spike's prefix tenancy, DDL, credentials, probe routes and ExUnit-specific exception handling in test support. Avoid introducing a token/session table. Validate duplicate JSON member handling and confirm the acceptable clock skew/token lifetime with VGAS-9 before staff use.
